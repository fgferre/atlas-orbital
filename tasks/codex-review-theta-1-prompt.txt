# Independent review — Phase θ.1 star sprite kernel port (atlas-orbital)

Atlas-orbital is a Three.js / R3F / TypeScript space visualizer. Phase θ
is a 15-onda effort to port highest-impact visual techniques from Gaia
Sky's GLSL / Java / LibGDX stack. θ.1 is the star sprite kernel.

**Context you need.** On 2026-04-20 seven Phase-θ commits were rolled
back because I had shipped θ.1 / θ.2 / θ.6 without reading the actual
Gaia Sky source — I had invented procedural shaders from the plan
prose. The user's verdict was "you're inventing code instead of
porting". The commit you are reviewing is the redo of θ.1 alone, done
under the "read Gaia Sky source before writing code" discipline that
the rollback taught.

The prior θ.1 attempt (`3b18c3e` + `542c846`, now gone from main) used a
`smoothstep(0.0, 0.5)` pixel-space core that does not appear anywhere
in Gaia Sky's actual shader. The new port replaces that with the real
kernel from `assets/shader/star.group.quad.fragment.glsl`, inlined
below.

**Review axes (unbiased — no rubber stamps).** Call out every defect,
vício, blindside, dead code, test gap, doc drift. Rank Alta / Média /
Baixa. Ambiguity gets a separate list.

1. **Plan-vs-source fidelity.** The port claims verbatim math of
   star.group.quad.fragment.glsl (the full 57-line source is inlined
   in §3). Does the ported GLSL match the source in the relevant parts
   — core smoothstep edges `(0.0, 0.04)`, additive-to-RGB core
   composition, `alpha = v_col.a × profile`, discard gate, UV space?
   Where the port diverges, is the divergence classified under one of
   {stack/API mismatch, pipeline/render-space, tier/perf gate, a11y}
   per the kickoff R1 step-5 rule, or is it invention in disguise?

2. **Shader correctness under three.js blending.** The fragment outputs
   `vec4(vColor + core*2, alpha)` and the material uses
   `THREE.AdditiveBlending` (which resolves to blend factors
   `SrcAlpha, One`). I'm claiming the visual effect is equivalent,
   pixel-for-pixel, to Gaia Sky's `fragColor = saturate(alpha *
   vec4(rgb + core*2, 1.0))` under their documented
   `BlendMode.ADDITIVE = GL_ONE, GL_ONE`. Verify the equivalence. If
   there is a blend-math blindside (e.g. the SrcAlpha factor
   re-applying alpha to the rgb output vs. pre-multiplied One/One), I
   want to know before the next onda builds on this.

3. **Gaussian σ choice.** The texture is 64×64 R8 built via a
   process-wide Uint8Array cache, σ = 10 pixels. UV-radius footprint:
   100 % at centre, ~29 % at r_uv=0.25, ~0.7 % at r_uv=0.5. That is
   materially wider than the pre-Wave-α `pow(d, 5)` ball (~3 % at
   r_uv=0.25) but tighter than σ=12 which produced visible haze on a
   first pass. Is σ=10 well-calibrated against Gaia Sky's typical
   `tex/base/star-tex-NN.{jpg,png}` aesthetic? Any L13 (hard-floor
   haze) / L14 (magnitude ordering) concern?

4. **L-lesson compliance.** L14, L15, L17 are all cited by the commit
   message. Sections are inlined in §4. Verify each on the actual
   code.

5. **Scope accounting (R7 honest-commit).** The commit message lists
   what was DEFERRED (Playwright `starfield-sprite.spec.ts`, visual
   reference fetching). Is any deferred item actually part of θ.1's
   effect core (which R7 forbids cutting) rather than adjacent
   surface (which R7 allows)? The θ.1 effect is defined as "Gaia
   Sky's per-star sprite kernel in the HYG Starfield"; adjacent
   surfaces are DisplayPanel rows, Playwright spec harness, and PNG
   baseline capture.

6. **Dead code / doc drift.** Any leftover from the old pow(d,5)
   fragment? Plan §5 θ.1 — inlined in §2 — after the rewrite, does
   every concrete claim (edges, compositing, references, risks) agree
   with the shipped shader? An Alta finding here is ANY shader
   behavior the plan still describes wrongly.

7. **HDR pipeline interaction (Wave α).** Renderer is `NoToneMapping`,
   composer has AgX last. Bloom runs with `luminanceThreshold = 1.0`
   on the selective buffer. The new kernel outputs `vColor + core*2`
   where vColor already carries `vfxHdrGain` per the vertex stage, so
   peak rgb can exceed 1.0 and will trigger Bloom. This is intended —
   but verify the kernel doesn't silently over-drive the bright pass
   (e.g. a mag-4 star with `vfxHdrGain = 2` and `core = 1` producing
   rgb ≈ 4, then bloom amplifying). Spot-check the combined math.

8. **Test coverage.** 5 new unit tests pin `starfieldCoreKernel`.
   Are the edges tested in the right places? Is the monotonicity
   test strict enough that a refactor to the smoothstep couldn't
   silently drift? Are there obvious additional anchors (e.g. pinning
   `smoothstep(0,0.04,0.01)` for a mid-curve sample)?

Where you find a defect, please propose the one-line diff (if small)
or the area to revisit (if structural). Mixed verdicts are fine —
apply-safe vs. flag-for-the-user is not your call, it's mine.

Notes on the source:
- `u_starTex` is loaded by `StarSetQuadComponent.setStarTexture()` from
  `tex/base/star-tex-NN.{jpg,png}` (asset bundle, external) with
  `Texture.TextureFilter.Linear, Texture.TextureFilter.Linear`. The
  atlas port substitutes an in-process 64×64 radial-gaussian
  `THREE.DataTexture` for the same slot.
- `v_col` is set by the vertex (`star.group.quad.vertex.glsl`,
  reproduced below for completeness; atlas re-uses its existing
  NASA-Eyes-calibrated log-compressed transfer in the vertex stage, so
  only the fragment is ported):

```glsl
__GAIA_SKY_VERTEX_PLACEHOLDER__
```

- Gaia Sky's `BlendMode.ADDITIVE = GL_ONE, GL_ONE` (verified in
  `core/src/gaiasky/render/BlendMode.java`). Atlas uses three.js
  `THREE.AdditiveBlending` which resolves to blend factors
  `SrcAlpha, One`. The commit claims these produce equivalent output
  under the chosen fragment form.
