### Specific questions to evaluate

#### A. Refactor feasibility (T6.1)

The design claims ~8 hardcoded uniforms in `ProceduralSun3D.tsx` need
externalizing:

- `uTint = 0.2`, `uBase = 4`, `uBrightnessOffset = 1`, `uBrightness = 0.6`
  (lines 399-401 in the surface noise material)
- `uHue = 0.2`, `uHueSpread = 0.2` (rays, lines 460-461)
- `uHue = 0` (flares, line 489)
- Perlin noise: `uSpatialFrequency = 6`, `uTemporalFrequency = 0.1`,
  `uH = 1`, `uContrast = 0.25`, `uFlatten = 0.72` (lines 370-375)
- Glow: `uRadius = 0.4`, `uTint = 0.4`, `uBrightness = 1.06` (lines 424-426)
- Ray/flare widths: lines 454-486

Questions:
- Are there OTHER hardcoded constants the Sonnet research missed that
  would also need to be externalized for non-Sun stars to render
  correctly? (E.g. sphere segments, depth bias, blending modes,
  geometry construction assumptions.)
- Is `lightDirWorld = new THREE.Vector3(1, 1, 1).normalize()`
  (line 322) actually a problem for non-Sun stars? Or is it
  irrelevant since the Sun is the lighting source for solar-system
  bodies but stars don't have other-body lighting on their own
  surface in atlas's scene?
- The `<group>` is scaled by `sunVisualRadiusWorld / SPHERE_RADIUS`
  at line 570. Does this scaling chain interact correctly with
  per-star MeshStandardMaterial defaults if the stellar mesh is
  parented to a HYG-position node 1+ kpc from origin?

#### B. Stellar physics correctness (T6.2)

The design proposes deriving from B-V:
- `temperatureFromBV(bv)` via Ballesteros formula
- `spectralClassFromTemperature(t)` via empirical thresholds
- `mainSequenceRadiusFromTemperature(t)` via Stefan-Boltzmann +
  main-sequence assumption

Questions:
- The Ballesteros formula has known limits — it's calibrated for
  main-sequence stars. HYG includes giants (e.g. Betelgeuse,
  Antares), sub-dwarfs, and the occasional white dwarf. What
  fraction of HYG breaks the formula's range? Is it acceptable
  to ship MVP knowing some stars render with the wrong color?
- Stefan-Boltzmann main-sequence radius assumes L = 4πR²σT⁴ AND
  a mass-luminosity relation (L ∝ M^3.5 for main-sequence). For
  giants this is very wrong (Betelgeuse: predicted ~10× wrong).
  Should the MVP include a luminosity-class detector (giant vs.
  dwarf vs. white dwarf) that uses HYG fields atlas already has?
- Spectral class thresholds: the design proposes hardcoded T_eff
  windows. Is this acceptable, or should it use a Morgan-Keenan
  table interpolation?
- HYG actually has a `spect` field (spectral class as a string
  like "G2V" or "M5III") in the v3 raw catalog. atlas's binary
  parser at `src/utils/hygBinary.ts` may have dropped this field.
  If we re-include it, can we skip `temperatureFromBV` entirely
  and parse class directly?

#### C. Atlas-architectural risks (T6.3)

The design proposes a camera-distance-gated mesh swap:
- When dist < `STELLAR_MESH_THRESHOLD_PARSECS`, spawn a procedural
  mesh; suppress the sprite for that one star.
- On zoom-out, dispose mesh + resume sprite.

Questions:
- atlas's `Starfield.tsx` renders the entire HYG catalog as a
  SINGLE instanced billboard mesh (~10k-110k stars in one draw
  call). Suppressing one star means writing a "skip" flag into
  one instance's attribute and re-uploading the buffer. Is this
  a perf concern at the focused-star transition? Or trivially
  cheap (1 float write + bufferAttribute.needsUpdate = true)?
- atlas's R3F lifecycle: spawning a procedural `<group>` with
  multiple internal meshes/materials inside a useEffect creates
  GPU resources that must be disposed on zoom-out. Per
  `lessons.md` M4 hot-path hygiene + L26 leak risk, what's the
  cleanest pattern? `useMemo + useEffect dispose return`, or
  a global cache keyed by star ID?
- atlas's focus system: does it currently support focusing on
  a HYG star? If yes, where (look for HYG-id → focus dispatcher).
  If no, does T6.3 need to add a focus-system extension as a
  pre-req?
- The Sonnet research treats `ProceduralSun3D` as an R3F
  component you mount per-star at the star's world position.
  But ProceduralSun3D was designed for ONE Sun at the scene
  origin. Multi-instance rendering (N stars each with their own
  ProceduralSun3D) — does it scale? Memory, draw calls,
  per-frame uniform writes? Or does atlas need a shared
  geometry + per-instance attributes pattern?
- Threshold value (`STELLAR_MESH_THRESHOLD_PARSECS`): the design
  hand-waves "~10 pc?". For a 0.001 R_sun white dwarf vs a 1000
  R_sun supergiant, the apparent angular size at 10 pc differs
  by 6 orders of magnitude. Should the threshold be solid-angle-
  based (matching Gaia's pattern) instead of distance-based?

#### D. Gaia-fidelity check

atlas's prior T4.9 audit (preserved in ROADMAP §T4.9) traced Gaia's
actual Sun-render path:
- `BillboardRenderer` (star-tex-04 sprite at stellar distances)
- `SingleStarQuadRenderer` (close-range Sun mesh from `default-data`)
- `StarSetInstancedRenderer` (catalog stars as instanced sprites)
- `VariableSetInstancedRenderer` (variable-star sub-pipeline)

Questions:
- Does Gaia have a "close-range procedural mesh for ANY HYG star"
  path, or only for hand-curated bodies in `default-data`
  (Sun, Proxima, etc.)? Search `core/src/gaiasky/` for evidence.
- If Gaia only has procedural close-range for hand-curated bodies,
  then atlas's T6 generalizes BEYOND Gaia. Is this scope creep
  (should we instead curate a small list of close-stars and ship
  that)? Or is generalization the right call given atlas's HYG
  catalog is the primary star data source (no per-star curation
  exists today)?
- Gaia's `SingleStarQuadRenderer.java` does what atlas plans for
  ProceduralSun3D adaptation — read it. What does it parameterize?
  What does it hardcode? Are there constants atlas's T6.1 misses?

#### E. Test strategy

The design implies tests for T6.1 (Sun-default-profile regression
guard), T6.2 (pinned values for known stars), T6.3 (threshold
logic). Questions:
- What's the smallest set of "known stars" atlas should pin in
  T6.2 tests? Suggested: Sirius A, Vega, Sun, Proxima Cen,
  Betelgeuse — covers G2V, A0V, A1V, M5.5V, M2I (giant). Good
  enough?
- For T6.3 mesh-spawn lifecycle, can the test harness exercise
  the spawn/dispose chain in jsdom, or does it require a real
  WebGL context? (atlas's vitest config uses jsdom for most
  shader tests via mocked Three.js).
- Should there be a runtime smoke step beyond compile/render —
  e.g. zoom-in/zoom-out cycle to verify dispose actually runs?
