## M1 — Sphere shader → modelViewMatrix (precision fix) ✅ PASS

**Effort**: ~30min-1h (actual: ~1h incl. dev-exposure smoke +
Codex audit).
**Scope tag**: Gaia-informed (Three.js `modelViewMatrix` is
the `ParticleSet.fetchPosition` analog).
**Status**: DONE 2026-05-05 (commit pending). Verified via
preview-MCP smoke at HYG focus `hyg:0` (Sirius, world position
~5.3×10^8 atlas units). Mesh visible after fly-to + zoom; gate
fired (`meshActive: true`, `sa: 0.040` at distToCamera=194).
Sun-at-origin still renders identically.

Minimal change to validate the precision hypothesis. Replaced
`gl_Position = projectionMatrix * viewMatrix * (modelMatrix * vec4(position, 1.0))`
with `gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0)`.

Three.js computes `modelViewMatrix` CPU-side as
`cameraMatrixWorldInverse × objectMatrixWorld` via
`Matrix4.multiplyMatrices` (plain JS, float64). Translation column
of result = `(objPos - cameraPos)` computed in float64 (precise
small value), cast to float32 only for GPU upload — same trick
Gaia uses, leveraging Three.js's existing infrastructure instead
of porting Vector3Q quad math.

The `vWorld` varying for fragment side became `vViewPos`
(camera-relative). Fragment's
`vec3 Vview = normalize((viewMatrix * vec4(vWorld - cameraPosition, 0.0)).xyz)`
became `vec3 Vview = normalize(vViewPos)`.

**Files touched**:

- `src/components/canvas/shaders/proceduralSunShaders.ts` —
  sphere vertex (lines 156-210) + fragment (lines 212-284). Glow
  / rays / flares unchanged (M2 territory).
- `.gitignore` — added `.codex/config.toml` (Codex audit P2 sweep).

**Codex audit (gpt-5.5, `codex exec review --uncommitted`)**:
clean for shader; 1 P2 — untracked `.codex/config.toml` not
gitignored (would leak `danger-full-access` if committed).
Addressed in same commit via `.gitignore` line.

**Acceptance** (met): clicking Sirius → camera flies → procedural
sphere mesh appears (visible, not invisible). Validated via
preview-MCP screenshot at `hyg:0` focus + zoom; orange disc
clearly rendered with skipMask suppressing the sprite slot 0.
M1 PASS, proceed M2.

## M2 — Glow + rays + flares shaders camera-relative ✅ PASS

**Effort**: ~2-3h (actual: ~2h incl. Codex P1 GLSL ES 1.0
compatibility fix).
**Scope tag**: Gaia-informed (same modelViewMatrix pattern).
**Status**: DONE 2026-05-05 (commit pending). Verified via
preview-MCP smoke at both `sun` and `hyg:0` (Sirius) focus

- zoom: full procedural sun renders with sphere + glow + rays
- flares all visible at parsec-scale HYG positions; Sun-at-
  origin renders identically post-M2 (no regression). M1+M2
  together close the visual-recovery precision-collapse failure
  mode.
  **Depends on**: M1 PASS ✓ (commit 74d6cea).

Applied modelViewMatrix pattern to all 3 billboard shaders.
Glow's `vec3 toCamera = normalize(center - cameraPosition)`
became view-space `vec3 toCenterView = normalize(centerView)`
where `centerView = (modelViewMatrix * vec4(0,0,0,1)).xyz`.
Camera-up `uCamUp` (world-space) became canonical view-space
`(0,1,0)` and the uniform was removed from JS (`cameraUpRef`

- per-frame setter also dropped). Rays' `vec3 vW = normalize(p0w

* cameraPosition)`became view-space`vec3 vView = normalize(p0v)`where`p0v = (modelViewMatrix \* vec4(p, 1.0)).xyz`. Flares
  similar.

### Coordinate-space contract (per Codex round-3 P2, applied)

Shipped option (2): geometry in view space, lighting dot-product
in world space using `vNormalWorld` (glow) / `vNormal` (rays,
flares). Each billboard vertex computes its outward radial
direction in view space, then converts to world via
`outwardView * mat3(viewMatrix)` — mathematically identical to
`transpose(mat3(viewMatrix)) * outwardView` but **GLSL ES 1.00
compatible**: `transpose()` is a GLSL ES 3.00+ builtin, and
atlas's ShaderMaterial path is on the WebGL1 baseline. Codex
audit P1 caught this; the fix was a syntactic-only swap. Contract
pinned in shader comments at every site (glow-vertex header,
glow-fragment header, rays-vertex inline, flares-vertex inline).

### Glow normal correctness sub-fix

The pre-M2 glow fragment did `getAlpha(normalize(vWorld))`,
treating world-space position as a normal. For Sun-at-origin
this approximated the outward radial direction (since the Sun
is at world origin); for HYG stars at parsec scale, `vWorld`
was dominated by the star's position offset and the dot-product
became meaningless. M2 introduces `vNormalWorld` as a true
per-fragment outward radial varying. Visible only as a
correctness improvement once HYG meshes render (post-M1).

  - per-frame `glowMaterial.uniforms.uCamUp.value.copy(...)`.

## M3 — Smooth sprite ↔ mesh cross-fade

**Effort**: ~2-3h.
**Scope tag**: atlas-native.
**Status**: pending.
**Depends on**: M2 PASS.

Replace `a_skipMask` Float32 0/1 binary with `a_fadeAlpha`
Float32 [0..1] continuous. Sprite multiplies its alpha by
`(1 - a_fadeAlpha)`. Mesh's `uVisibility` ramps 0→1 in parallel
to `a_fadeAlpha` 0→1. Hysteresis still gates direction of the
ramp (sa > ENTER → ramp toward 1, sa < EXIT → ramp toward 0);
cushion prevents oscillation. Fade duration ~300ms (or smoothstep
over the small ENTER..EXIT solidAngle band).

### Threshold coordination — focused-star-specific (per Codex round-3 P2)

The LEN0/ENTER 1:17 ratio gap was diagnosed for the FOCUSED star
path. Globally lowering `u_LEN0` or raising `STELLAR_MESH_ENTER_RAD`
would affect EVERY sprite + EVERY mesh activation in the catalog
(perf regression risk — LEN0 controls hard-zero of sprites at
very small angular sizes; mesh ENTER affects gate timing for the
entire HYG focus mechanism).

Instead: keep LEN0 + ENTER global constants unchanged; introduce
a focused-star-specific fade window. HygStellarMesh tracks a
ramp progress in a ref (0..1, increments toward 1 when
`solidAngle > ENTER`, decrements toward 0 when `< EXIT`, smooth
over ~300 ms). Per-frame writes `a_fadeAlpha[K] = ramp` for the
focused star K only — all other sprites stay at 0 (current
behavior). Mesh `uVisibility = ramp` in parallel.

Pin invariant in test: focused sprite alpha never reaches zero
before mesh ramp ≥ ε for some small ε; equivalently,
`(focused-sprite alpha + mesh visibility) > 0` throughout the
transition.

**Acceptance**: zoom-in to HYG star shows continuous sprite-to-
mesh visual transition with no pop, no gap, no flicker. User
smokes 2 zoom cycles per named star.

## M4 — Class variation in stellarVisualProfileFrom (perceptual distinction)

**Effort**: ~2-4h.
**Scope tag**: atlas-native.
**Status**: pending.
**Depends on**: M3 PASS (so transition smoothness is verified
before changing per-star visual identity).

Current implementation overrides only 3 fields (surfaceBrightness,
raysHue, flaresHue). Extend `stellarVisualProfileFrom` to make
each class perceptually distinct. Candidate fields to vary
(temperature-derived):

- granulation × 5: spatialFreq, temporalFreq, H, contrast, flatten
- surface × 6: tint, base, brightnessOffset, fresnelPower,
  fresnelInfluence, brightness
- glow × 4: radius, tint, brightness, falloffColor
- rays × 6: length, noiseFreq, noiseAmp, alphaBlended, hueSpread, hue
- flares × 6: amp, alphaBlended, hueSpread, hue, noiseFreq, noiseAmp

Pin per-named-star test cases (Sirius A1V → blue-white profile;
Betelgeuse M2Ia → deep red supergiant; Proxima M5.5V → red dwarf;
Sun G2V → byte-identical to SUN_DEFAULT_VISUAL_PROFILE).

### Acceptance reframe (per Codex round-3)

Goal is **PERCEPTUAL** class distinction — when user looks at
Sirius vs Betelgeuse vs Proxima vs Sun side-by-side, they look
distinctively different in color/size/brightness/corona character.
NOT all 28 fields literally must vary; some may stay solar if
they don't contribute to perceptual difference.

Acceptance: 4 named stars × 2 zoom cycles, each visibly
distinct; AND Sun-at-origin renders byte-identical to pre-M4
baseline (no perceptual regression for Sun). SUBAGENT VERIFY
confirms no per-star coupling bugs.

## M5 — Spect-missing fallback via absmag

**Effort**: ~2-3h (Path B + Path A combined).
**Scope tag**: atlas-native.
**Status**: pending.
**Depends on**: independent of M1-M4 (data fix), can run in
parallel; but easier to user-smoke after M4 so visual identity
is tied together.

### Premise correction (per Codex round-3 P2)

Original M5 plan claimed `radiusFromSpect(null, absmag)`
"already supports absmag fallback" — **false**.
`stellarPhysics.ts:369` does `if (!spect) return 1.0;` BEFORE
looking at absmag. The absmag parameter is consumed only by the
optional Stefan-Boltzmann refinement path (line ~402+) which
runs AFTER class-table lookup, i.e., only when spect IS present.
With spect="", absmag is never read.

M5 must do real work, not extend an existing path.

### Path A — runtime absmag fallback (~1-2h)

Extend `radiusFromSpect(spect, absmag)` to accept the
missing-spect case. When `spect` is null/empty AND `absmag` is
finite, derive an estimated radius from absmag alone using a
B-V-augmented Stefan-Boltzmann path (atlas already has B-V at
HygStellarMesh call site, can pass it through; or compute T_eff
from B-V via `temperatureFromBV` and combine with absmag for
L/L_sun then `R/R_sun = sqrt(L) × (T_sun/T_eff)²`). This handles
ANY star with missing spect, not just named ones. Pin per-named-
star radius assertions: Betelgeuse, Antares, Rigel, Proxima from
absmag+B-V should produce supergiant-class radii within ~30% of
catalog literature values.

### Path B — preserve named stars at canonicalization (~1h)

Fix `scripts/build-hyg-binary.js` `capSpectByFrequency` so it
always keeps the canonical class of any star in
`hyg-v1.names.json` (allowlist by HIP/proper-name/index — note:
the names sidecar today carries `hip` + `proper` + `bayer` +
`flam` + `con` + `index`; HD field is NOT exposed there, so
allowlist must use the available keys). Re-bake the 4 tier
`.bin` files. T6.2-β-β already showed how to re-bake; M5-B is a
delta. Net effect: Betelgeuse/Antares/Rigel get their real spect
strings restored in the binary; existing `radiusFromSpect(spect)`
does the right thing without runtime fallback work. Costs an L32
PNG re-bake flag (binary file change → screenshots if any depend
on starfield rendering — but they don't).

### Recommended: Path B + Path A combined

Path B fixes the specific-named-star regression that drove M5;
Path A is a defensive runtime fallback for any unnamed star
whose canonical class still ends up empty.

**Acceptance**: Betelgeuse renders supergiant-sized (~887 R_sol)
not Sun-sized. Same for Antares (~680 R_sol), Rigel (~78 R_sol),
Proxima (~0.15 R_sol). Pin per-star radius assertions in
`stellarPhysics.test.ts`.

## M6 — HygStarPanel info panel (OPTIONAL — see scope note)

**Effort**: ~2-3h.
**Scope tag**: atlas-native.
**Status**: pending, OPTIONAL.

### Scope note (per Codex round-3 reframe)

M6 is UX addition, NOT part of render-recovery root cause. The
visible T6 failure (mesh invisible) is fixed by M1+M2; the
smooth-transition gap by M3; class distinction by M4; supergiant
sizing by M5. M6 adds a HYG-side info panel for completeness of
the user-expectation conversation but does NOT block declaring

Implementation order: M1→M2→M3→M4→M5 first; user smokes after
M5 and confirms recovery; THEN M6 ships as polish IF user judges
the panel worth the time. Treat M6 as gate-able post-M5.

### API note (per Codex round-3 P3)

Original M6 plan referenced `stellarPhysicsFrom` — that helper
does NOT exist. `stellarPhysics.ts` exports lower-level helpers:
`parseSpectralClass`, `temperatureFromSpect`, `temperatureFromBV`,
`radiusFromSpect`, plus the visual aggregator
`stellarVisualProfileFrom`. M6 must EITHER (a) compose panel
data directly from those individual helpers — **recommended**,
keeps stellarPhysics.ts focused on visual-profile concerns —
OR (b) introduce a new aggregator (e.g.
`derivePanelPhysics(input)`) that bundles
spect+B-V+absmag → {className, tEff, rSolar, mSolar, distancePc,
...}. Don't pretend `stellarPhysicsFrom` already exists.

### Component spec

New component analogous to existing `Sidebar` but driven by
`hyg:K` focus IDs instead of `BODIES_BY_ID`. Reads catalog +
sidecar data + composes per-field display values from individual
stellarPhysics helpers (or new aggregator). Displays:

- Common name (sidecar `proper`/`bayer`/`flam`/`con`)
- Spectral class (parsed) + raw spect string
- Effective temperature (Ballesteros + MK refinement)
- Radius in R_sol
- Mass estimate from class + absmag
- Distance in parsec
- Apparent + absolute magnitude
- Sun comparison row ("Betelgeuse is 887× Sun radius")

Sidebar is HYG-blind today (resolves via BODIES_BY_ID); render
HygStarPanel as a parallel slot, gated on
`parseHygFocusId(focusId) !== null`.

**Acceptance**: focus a HYG star → panel populates with all
fields; panel hides on focus to curated body (existing Sidebar
takes over).
