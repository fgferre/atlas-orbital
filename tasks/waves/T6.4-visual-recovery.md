## M1 — Sphere shader → modelViewMatrix (precision fix) ✅ PASS

**Effort**: ~30min-1h (actual: ~1h incl. dev-exposure smoke +
Codex audit).
**Scope tag**: Gaia-informed (Three.js `modelViewMatrix` is
the `ParticleSet.fetchPosition` analog).
**Status**: DONE 2026-05-05 (commit `74d6cea`). Verified via
preview-MCP smoke at HYG focus `hyg:0` (Sirius, world position
~5.3×10^8 atlas units). Mesh visible after fly-to + zoom; gate
fired (`meshActive: true`, `sa: 0.040` at distToCamera=194).
Sun-at-origin still renders identically.

Minimal change to validate the precision hypothesis. Replaced
`gl_Position = projectionMatrix * viewMatrix * (modelMatrix * vec4(position, 1.0))`
with `gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0)`.

Three.js computes `modelViewMatrix` CPU-side as
`cameraMatrixWorldInverse × objectMatrixWorld` via
`Matrix4.multiplyMatrices` (plain JS, float64). Translation column
of result = `(objPos - cameraPos)` computed in float64 (precise
small value), cast to float32 only for GPU upload — same trick
Gaia uses, leveraging Three.js's existing infrastructure instead
of porting Vector3Q quad math.

The `vWorld` varying for fragment side became `vViewPos`
(camera-relative). Fragment's
`vec3 Vview = normalize((viewMatrix * vec4(vWorld - cameraPosition, 0.0)).xyz)`
became `vec3 Vview = normalize(vViewPos)`.

### Coordinate-space contract (per Codex round-3 P2, applied)

Shipped option (2): geometry in view space, lighting dot-product
in world space using `vNormalWorld` (glow) / `vNormal` (rays,
flares). Each billboard vertex computes its outward radial
direction in view space, then converts to world via
`outwardView * mat3(viewMatrix)` — mathematically identical to
`transpose(mat3(viewMatrix)) * outwardView` but **GLSL ES 1.00
compatible**: `transpose()` is a GLSL ES 3.00+ builtin, and
atlas's ShaderMaterial path is on the WebGL1 baseline. Codex
audit P1 caught this; the fix was a syntactic-only swap. Contract
pinned in shader comments at every site (glow-vertex header,
glow-fragment header, rays-vertex inline, flares-vertex inline).

### Glow normal correctness sub-fix

The pre-M2 glow fragment did `getAlpha(normalize(vWorld))`,
treating world-space position as a normal. For Sun-at-origin
this approximated the outward radial direction (since the Sun
is at world origin); for HYG stars at parsec scale, `vWorld`
was dominated by the star's position offset and the dot-product
became meaningless. M2 introduces `vNormalWorld` as a true
per-fragment outward radial varying. Visible only as a
correctness improvement once HYG meshes render (post-M1).

### Scope discipline (per Codex 2026-05-05 review)

This is **NOT** a full AAA navigation rewrite. The scope is
specifically: replace the snap+Bézier+single-channel HYG fly-to
with a Gaia-informed two-channel transition that respects the
Atlas mesh-spawn gate. "Gaia-informed" rather than "Gaia-faithful"
because the orientation channel is an OrbitControls-native
approximation of Gaia's quaternion slerp, not a port (see Codex
round-3 §C-3 below). Curated-body fly-to stays untouched.
The interactive/scripted "go-to-object continuous push" mode
from Gaia's `InteractiveCameraModule` is out of scope — Atlas
uses pre-computed transitions, not REPL-style camera scripting.

### Why this milestone exists (2026-05-05)

User smoke after M1+M2 surfaced that the HYG fly-to feels
janky despite the mesh now rendering correctly. Source trace
of the existing path (`CameraController.tsx:230-317` plus
`CameraTransition.ts`) plus reading the actual Gaia Sky source
identified six root causes:

1. **Orientation snap pre-animation**: `controls.target.copy(targetPos)`
   at `CameraController.tsx:315` runs BEFORE
   `transitionRef.start()`. The camera "rotates instantly" to
   look at the star while position is still translating —
   classic spin-then-glide feel.
2. **Single-channel transition**: `CameraTransition` interpolates
   only position. Three.js `OrbitControls` derives orientation
   from `target`; with target snapped, orientation has no
   independent timing.
3. **Sun-avoidance Bézier control point**:
   `CameraTransition.ts:56-86` pushes the curve away from the
   Sun. Designed for solar-system geometry; at parsec scale
   the Sun is one star among many and the arc looks weird.
4. **Asymmetric easing** `easeOutQuint`: starts fast, ends
   slow. Cinematic feel needs a symmetric S-curve (sigmoid)
   so both ends feel deliberate.
5. **Fixed target solid angle**: Atlas computes
   `idealDist = radius / (STELLAR_MESH_ENTER_RAD * 5)` ≈
   0.286° apparent size. Far stars and near stars get the
   same target → near stars land smaller than they should,
   far stars larger (or below the gate).
6. **Hard duration cap (4s) regardless of distance**: an
   interstellar fly-to from solar system to a 100-pc star
   gets the same time budget as a fly-to within the solar
   system. Position scale-aware duration is missing.

### Spec

#### S1 — Angle math + Atlas mesh-spawn clamp (~1.5h, shipped at `c44cebe` + Codex round-1 correction + Codex round-3 angular-radius fix)

`src/lib/camera/stellarFlightSolidAngle.ts`. Two-layer contract:

1. **Gaia-informed**: `computeGaiaTargetAngularRadiusRad(distancePc)`
   returns the ANGULAR RADIUS in radians from the lerp
   `1.0° at 1.31 pc → 0.001° at 2805 pc`. Source:
   `InteractiveCameraModule.java:158-172` compared against
   `ParticleSet.java:809` (`focusSolidAngle =
(radius/distance)/fovFactor` — angular-radius semantics
   despite the misleading name). "Gaia-informed" rather than
   "Gaia-faithful" because Gaia normalises by
   `camera.getFovFactor()` and computes radius from a
   pseudo-size (`size × STAR_SIZE_FACTOR`,
   `ParticleSet.java:785`); Atlas drops the fovFactor
   normalisation and uses physical radius from `radiusFromSpect`.
   Both divergences are pinned in the lib header.
2. **Atlas-clamped**: `computeAtlasFlightTarget(distancePc)`
   wraps Gaia's target with a floor at the procedural-mesh
   spawn gate. Without the clamp, a star at the far anchor
   (Gaia 0.001° angular radius = 1.745e-5 rad) lands far
   below `STELLAR_MESH_ENTER_RAD = 1e-3` and the procedural
   mesh NEVER spawns — the camera arrives correctly per Gaia
   but T6 visual recovery silently regresses for distant
   stars. The clamp ensures
   `angularRadiusRad ≥ STELLAR_MESH_ENTER_RAD × 5`, which
   matches the 5× hysteresis margin the pre-M2.5
   `CameraController.tsx` already used.

Convenience composer
`computeAtlasFlightLanding(radiusWu, distancePc)` returns
`{ distanceWu, target: { angularRadiusRad, clampedByAtlasFloor }
}` so the camera controller (S4) can log which clamp
dominated.

**Angle semantics — pinned in lib header to prevent
re-confusion** (Codex round-3, 2026-05-05, after the M2.5
first-draft confused angular radius with full angle):

- **Angular radius** (apparent radius) — the unit Gaia's
  `getSolidAngle()` actually returns despite its name, and the
  unit Atlas's mesh-spawn gate compares against. The lerp
  anchors (1.0°, 0.001°) live in this space.
- **Full angle** (apparent diameter, = 2 × angular radius) —
  NOT used in this lib post-Codex-round-3. The first-draft
  M2.5 lib treated the Gaia anchors as full angle and halved
  them, producing a 2× landing-distance regression for every
  HYG fly-to.
- **Solid angle** (sr) — area on the unit sphere. NOT used
  here; the unfortunate `solidAngle` name in Gaia's source is
  preserved only in historical-reference comments.

Crossover where Gaia's adaptive angular radius equals the
Atlas floor sits at ~2003 pc (post-Codex-round-3). Below that
distance the camera lands per Gaia (closer than pre-M2.5 —
Sirius lands at ~456 wu vs pre-M2.5 ~1593 wu, a ~3.5× ratio).
Beyond, it lands at the pre-M2.5 floor exactly (no regression).

Tests pin: anchor constants byte-equal to Gaia source, lerp
behavior at exact anchors + midpoint + clamp regions,
named-star landings (Sirius, Betelgeuse, Proxima, Sun-at-
far-anchor), crossover behavior near 2003 pc, mesh-spawn
floor never violated across the full distance range. The
"regression vs Atlas pre-M2.5" pin uses the **correct**
pre-M2.5 angular radius (5e-3 rad), giving the ~3.5× ratio
above. The Codex-round-1 corrected commit pinned ~1.74×
because the lib was still halving the Gaia curve — that
mid-state was wrong; round-3 dropped the halving and
restored the original ~3.5× ratio.

#### S2 — Logistic-sigmoid easing (~30min, shipped at `e6d35de`)

Added `CameraTransition.logisticSigmoid(t, factor=12)` static
method (`src/lib/camera/CameraTransition.ts:185-211`). 13 unit
tests pin endpoint clamps (`logisticSigmoid(0) === 0`,
`logisticSigmoid(1) === 1`), midpoint symmetry, point-symmetry
around (0.5, 0.5), monotonicity, [0, 1] bounds, S-curve
character at t∈{0.05, 0.4, 0.6, 0.95}, factor parameter
behavior (default 12 vs Gaia 60), and the raw-sigmoid formula
match. Atlas-Gaia divergence (intentional): `factor` defaults
to 12 (not Gaia's 60) because Gaia's 60 plateaus at the
endpoints for ~30% of the duration on 4-6s transitions; 12
keeps clear S-character without the stall. Endpoints clamped
via affine renormalization
`(sig(t) - sig(0)) / (sig(1) - sig(0))` so the start/end frames
don't visually freeze.

#### S3 — Two-channel `StellarFlightTransition` (~2h)

New class in `src/lib/camera/StellarFlightTransition.ts` with
separate position and orientation channels. API:

```ts
interface StellarFlightSpec {
  startPos: Vector3; // current camera world position
  endPos: Vector3; // landing position (from S1's
  // computeAtlasFlightLanding)
  startTarget: Vector3; // current OrbitControls target
  endTarget: Vector3; // star world position
  posDurationMs: number;
  oriDurationMs: number;
  posEasing?: (t: number) => number; // default logisticSigmoid
  oriEasing?: (t: number) => number; // default logisticSigmoid
  onComplete?: () => void;
}

class StellarFlightTransition {
  start(spec: StellarFlightSpec): void;
  /** @returns { position, target, done } each frame. */
  update(): { position: Vector3; target: Vector3; done: boolean } | null;
  /** Freeze both channels at current alpha and emit the
   *  intermediate state for the controller to read. */
  cancel(): { position: Vector3; target: Vector3 } | null;
}
```

**Why target instead of quaternion** (per S4's OrbitControls
coordination strategy, picked option 2): Three.js `OrbitControls`
derives camera orientation from `(camera.position, controls.target)`
and overwrites any direct quaternion change in its per-frame
`update()`. Animating quaternion directly would fight the
controls. Instead, the orientation channel outputs the lerped
`target` position; `OrbitControls.update()` then derives the
camera's actual orientation from it. The camera ALWAYS looks at
`controls.target` during the transition, which is exactly the
desired behavior (look at the destination star throughout
fly-to). No quaternion math needed at this layer.

Position interpolates a straight line `mix(startPos, endPos,
posEasing(alpha))` — no Bézier, no sun-avoid. Target
interpolates `mix(startTarget, endTarget, oriEasing(alpha))`.
Two alphas clamped against two durations; `done` is true when
both reach 1. `cancel()` freezes both at the current alpha so
S5's interrupt path can emit the intermediate values cleanly
(no snap-back, no jump-forward). Default easing is
`CameraTransition.logisticSigmoid` (S2).

#### S4 — `CameraController` HYG branch refactor (~2.5h)

Rewrite `setupCameraHyg()` ([`CameraController.tsx:230-317`](../../src/components/canvas/CameraController.tsx)).

**OrbitControls coordination strategy** (per Codex 2026-05-05
correction): Three.js `OrbitControls` derives camera orientation
from `(camera.position, controls.target)`. Animating
`camera.quaternion` directly via slerp would FIGHT
`OrbitControls` (which would re-derive the orientation from
`target` every frame and overwrite the slerp). Two valid
approaches:

1. **Suspend `OrbitControls` during the transition**, animate
   the camera's `quaternion` directly with slerp, then on
   completion compute a `controls.target` consistent with the
   final orientation and re-enable controls. Clean separation
   but adds a brief window where user input is ignored.
2. **Animate `controls.target` per frame** in lockstep with
   the camera position, so `OrbitControls`-derived orientation
   is the slerp result. The animated target follows a path
   from "current target" to "the focused star", easing on the
   orientation duration (independent of the position duration).
   `OrbitControls.update()` then produces the correct camera
   orientation each frame.

**Pick (2)** for minimum churn — no input suspension, the
existing `OrbitControls` damping continues to read sensible
values throughout. The tradeoff: orientation is constrained to
"look at controls.target", which is exactly what we want
(camera ALWAYS looks at the destination star during fly-to).

Concrete steps:

- Drop the `controls.target.copy(targetPos)` snap at
  [`CameraController.tsx:315`](../../src/components/canvas/CameraController.tsx).
- Compute landing distance via
  `computeAtlasFlightLanding(radiusWu, distancePc)` from S1.
  Apply body-clearance floor: final distance =
  `Math.max(radiusWu * 1.1, result.distanceWu)`.
- Compute scale-aware durations:
  ```ts
  const linearDist = startPos.distanceTo(endPos);
  const posDurationMs = clamp(Math.log10(linearDist + 1) * 1500, 2000, 8000);
  const angularSweep = (current target → star target) angular distance;
  const oriDurationMs = clamp(angularSweep * 2000, 1000, 4000);
  ```
- Update `near`/`minDistance` from the REAL star radius (not
  the `HYG_FOCUS_DEFAULT_RADIUS_WORLD` placeholder still used
  at
  [`CameraController.tsx:485-490`](../../src/components/canvas/CameraController.tsx)).
  Per Codex 2026-05-05: HYG fly-to currently falls back to
  the placeholder; M2.5 wires the real radius through.
- Hand off to `stellarFlightTransition.start(spec)`. Per-frame
  `useFrame` reads `update()`, applies the position lerp to
  `camera.position`, and the orientation lerp to
  `controls.target` (which `OrbitControls.update()` then
  consumes to derive the camera's actual quaternion).

#### S5 — Real interrupt with state preservation (~45min)

`OrbitControls "start"` event currently only flips
`isFlying = false`
([`CameraController.tsx:461-468`](../../src/components/canvas/CameraController.tsx))
— it does NOT cancel the transition or preserve intermediate
state. Result: when the user mouse-drags mid-flight, the camera
jerks because the position transition keeps running but the
target snap already happened on focus-set.

Real interrupt:

- Add `stellarFlightTransition.cancel()` which freezes both
  channels at their current alpha and emits the current state
  `{ position, target }` for the controller to read.

## M3 — Smooth sprite ↔ mesh cross-fade

**Effort**: ~2-3h.
**Scope tag**: atlas-native.
**Status**: pending.
**Depends on**: M2.5 PASS (smooth fly-to is a prereq for the
fade to be meaningful — a janky arrival makes any fade look
like a hack).

Replace `a_skipMask` Float32 0/1 binary with `a_fadeAlpha`
Float32 [0..1] continuous. Sprite multiplies its alpha by
`(1 - a_fadeAlpha)`. Mesh's `uVisibility` ramps 0→1 in parallel
to `a_fadeAlpha` 0→1. Hysteresis still gates direction of the
ramp (sa > ENTER → ramp toward 1, sa < EXIT → ramp toward 0);
cushion prevents oscillation. Fade duration ~300ms (or smoothstep
over the small ENTER..EXIT solidAngle band).

### Threshold coordination — focused-star-specific (per Codex round-3 P2)

The LEN0/ENTER 1:17 ratio gap was diagnosed for the FOCUSED star
path. Globally lowering `u_LEN0` or raising `STELLAR_MESH_ENTER_RAD`
would affect EVERY sprite + EVERY mesh activation in the catalog
(perf regression risk — LEN0 controls hard-zero of sprites at
very small angular sizes; mesh ENTER affects gate timing for the
entire HYG focus mechanism).

Instead: keep LEN0 + ENTER global constants unchanged; introduce
a focused-star-specific fade window. HygStellarMesh tracks a
ramp progress in a ref (0..1, increments toward 1 when
`solidAngle > ENTER`, decrements toward 0 when `< EXIT`, smooth
over ~300 ms). Per-frame writes `a_fadeAlpha[K] = ramp` for the
focused star K only — all other sprites stay at 0 (current
behavior). Mesh `uVisibility = ramp` in parallel.

Pin invariant in test: focused sprite alpha never reaches zero
before mesh ramp ≥ ε for some small ε; equivalently,
`(focused-sprite alpha + mesh visibility) > 0` throughout the
transition.

mesh visual transition with no pop, no gap, no flicker. User

## M4 — Class variation in stellarVisualProfileFrom (perceptual distinction)

**Effort**: ~6-9h (was ~2-4h pre-2026-05-05 spec revision; expanded
after live diagnostic of "todas amarelas" symptom + Codex pre-M4
review pulled the scope toward spectral-color-first).
**Scope tag**: atlas-native (visual identity is an atlas decision;
Gaia Sky's `starsurface.fragment.glsl` is a separate hardcoded
shader, not a port target).
**Status**: pending.
**Depends on**: M3 PASS (so transition smoothness is verified
before changing per-star visual identity).

### Diagnostic driving this revision (2026-05-05)

After M1+M2 shipped and HYG meshes started rendering, the user
observed every focused star renders the same yellow-orange disc
regardless of spectral class (Sirius A1V should be blue-white,
Betelgeuse M2Iab should be deep red supergiant, Proxima M5.5V
should be red dwarf — all looked solar). Source trace confirms
the gap:

1. **`stellarVisualProfileFrom`** ([stellarPhysics.ts:510-537](../../src/lib/stellarPhysics.ts))
   spreads `SUN_DEFAULT_VISUAL_PROFILE` and overrides only 3 of
   28 fields: `surfaceBrightness` (clamped to [0.4, 1.5] — too
   tight to drive perceived class difference), `raysHue` (offset
   ±0.4), `flaresHue` (same offset). The other 25 fields stay
   solar.
2. **`absmag` is accepted by the input but ignored** —
   `StellarPhysicsInput.absmag?` is declared but
   `stellarVisualProfileFrom` never reads it (and `radiusFromSpect`
   only consults absmag when `spect` is also present, falling
   back to `1.0` otherwise per [stellarPhysics.ts:367-369](../../src/lib/stellarPhysics.ts:367)).
3. **`brightnessToColor` is the dominant color source** in BOTH
   sphere ([proceduralSunShaders.ts:245](../../src/components/canvas/shaders/proceduralSunShaders.ts:245))
   AND glow ([proceduralSunShaders.ts:382](../../src/components/canvas/shaders/proceduralSunShaders.ts:382))
   fragments: `vec3(b, b², b⁴) * uBrightness`. `uTint` only
   modulates the relative magnitudes of the G/B channels but
   the formula is monotonic across channels — it CANNOT produce
   blue-dominant output regardless of `uTint`. So per-class
   color simply doesn't fit through this formula.
4. **All materials use `toneMapped: false`** ([ProceduralSun3D.tsx:409,448,483,523,565](../../src/components/canvas/ProceduralSun3D.tsx:409))
   — shader output is linear-RGB HDR; tone map is downstream.
   Any new color uniform MUST be in linear-RGB, NOT sRGB.

Conclusion: M4 cannot succeed by varying just the existing 28
profile fields. The hardcoded `brightnessToColor` formula must
yield to a per-class color uniform; the descriptor reaching
`stellarVisualProfileFrom` must include `absmag` + `luminosityClass`;
and granulation must split temperature-derived character (hue,
contrast tilt) from luminosity-class-derived structure (cell size,
time scale).

### Spec (revised post-Codex review)

#### S1 — Typed visual descriptor (TS-side, ~1h)

Replace ad-hoc `StellarPhysicsInput` shape with an explicit
`StellarVisualDescriptor` interface bundling everything the
visual profile actually needs:

```ts
interface StellarVisualDescriptor {
  tEff: number; // Kelvin — primary color driver
  spectralClass: SpectralClass; // O / B / A / F / G / K / M / L / T / Y / WD
  luminosityClass: LuminosityClass; // Ia / Ib / II / III / IV / V / VI / VII (or null)
  bv: number; // B-V color index — fallback for tEff
  absmag: number | null; // V-band absolute magnitude — drives glow intensity
  radiusSolar: number; // R/R_sun — informational + glow scaling
}
```

`luminosityClass` is the new field. Today `parseSpectralClass`
extracts it from spect strings like "G2V" or "M2Iab" but
`stellarVisualProfileFrom` ignores it. M5 (spect-fallback) needs
to surface it too.

Helper `descriptorFromCatalog(spect, bv, absmag)` builds the
descriptor from raw HYG fields; consumers use the descriptor.

#### S2 — Blackbody linear-RGB color (TS-side, ~1-2h)

Add `blackbodyRgbFromTemperature(tEff: number): [r, g, b]` in
linear-RGB space. Use a published table (e.g. CIE 1931 chromaticity
of Planck radiator → sRGB primaries → undo sRGB transfer) or a
piecewise polynomial fit (Krystek 1985 / Mitchell Charity table).
Pin per-named-star outputs in tests:

- Sun (5778 K) → close to current `brightnessToColor(1.0)` output
  in linear space. Pin numeric tolerance, NOT byte-identical
  (changing the formula breaks byte-identical; perceptually
  identical post-tone-map is the real requirement).
- Sirius (~9940 K) → blue-white tilt
- Betelgeuse (~3500 K) → deep orange-red
- Proxima (~3050 K) → reddish-orange (not deep red — M5.5V is
  cooler than Betelgeuse but per blackbody curve, not by much in
  the visible-band sense; deep-red perception is from low
  luminosity, not pure tEff)

Math lives in `src/lib/stellarColor.ts` (new file). Pure function,
fully unit-tested before reaching the shader.

#### S3 — Shader uniforms for class color (~1h)

Replace `brightnessToColor`'s color decision with a per-class
RGB uniform passed in linear space.

Sphere fragment proposed form:

```glsl
uniform vec3 uClassColor;  // linear-RGB blackbody, T6.4-M4
uniform float uClassWhitePoint; // brightness above which the
                                // surface saturates to white
                                // (HDR core look). Solar default
                                // matches current ~5.0.

vec3 brightnessToColor(float b) {
  // Lerp class hue to white at high brightness so the core stays
  // HDR-white (current visual character) while the limb / lower-
  // brightness regions show class color. Replaces the prior
  // (b, b², b⁴) formula which only spanned warm-yellow→white.
  vec3 hue = uClassColor;
  float saturation = 1.0 - smoothstep(1.0, uClassWhitePoint, b);
  vec3 chroma = mix(vec3(1.0), hue, saturation);
  return chroma * b * uBrightness;
}
```

Sphere AND glow must take the same uniform — otherwise the corona
color drifts from the surface. JS-side: `uClassColor` is set once
per focus change (not per-frame) since the descriptor is stable
while a star is focused.

Sun-default test vector: with `uClassColor = blackbodyRgb(5778)`,
the post-tone-map pixel-diff against the pre-M4 baseline must be
≤1% (roughly 1 sRGB unit per channel after the post-process
pipeline). This is the realistic substitute for byte-identical;
pin via Playwright pixel-diff in the named e2e spec.

#### S4 — `absmag` participates in glow intensity (~30min)

`absmag` is the V-band luminosity proxy. Hot-luminous stars
(Sirius A1V at M_V ≈ +1.4, Rigel B8Ia at M_V ≈ -7.8) should have
visibly brighter halos than equally-hot lower-luminosity stars.
Map `absmag` to a `glowBrightness` multiplier:

```ts
glowBrightnessScale = clamp(
  pow(10, -0.4 * (absmag - M_SUN_V_ABS) * 0.15),
  0.5,
  3.0
);
```

The 0.15 exponent damps the actual luminosity ratio so the visual
range stays usable (a true 10^(-0.4 \* ΔM) spans ~10^9 across the
catalog). Clamp [0.5, 3.0] keeps even ultra-faint M dwarfs visible
and ultra-bright supergiants from blowing out bloom. Pure
artistic factor — explicitly NOT a physics claim about coronal
luminosity.

#### S5 — Granulation: temperature × luminosity class (~2-3h)

Two-axis split:

- **Temperature** drives granulation **contrast** + **noise hue
  bias** (cool stars have stronger thermal contrast between cells
  and intercellular lanes; hot stars have radiative atmospheres
  with weak granulation visibility). Map `granulationContrast`
  and (optionally) a small surface-color modulation per cell.
- **Luminosity class** drives **cell size** (`spatialFreq`) and
  **time scale** (`temporalFreq`). Pressure scale height H_p
  scales as `~T_eff / g`; cell size scales with H_p. Supergiants
  (Ia/Ib/II) have huge H_p (low gravity at extended atmospheres)
  → very large cells, slow turnover (months on Betelgeuse vs
  ~5 min on Sun). Main-sequence (V) → cells matched to T_eff.
  White dwarfs (VII) → high g, tiny cells if any.

Approximate mapping (atlas-opinion, not physics):

| Class             | spatialFreq | temporalFreq | contrast |
| ----------------- | ----------- | ------------ | -------- |
| Ia (supergiant)   | 1.5         | 0.02         | 0.45     |
| III (giant)       | 4           | 0.06         | 0.35     |
| V (main sequence) | 6           | 0.10         | 0.25     |
| VII (white dwarf) | 12          | 0.20         | 0.10     |

Hot main-sequence (O / B / A) gets contrast scaled down by
~`exp(-(tEff - 6000) / 4000)` to flatten the surface — radiative
atmospheres look smoother. Pin per-named-star output in tests.

#### S6 — Glow / rays / flares as class+activity art (~1h)

Frame as art-direction layer, not physics:

- **Glow `falloffColor` + tint**: O/B → cleaner, sharper falloff;
  K/M → softer, broader halo (chromospheric activity look).
  Driven by `tEff` curves, not blackbody dictates.
- **Rays amplitude**: low for hot main-sequence (clean look); higher
  for K/M dwarfs (active corona); slow + wide for supergiants.
  Scale by both class AND `absmag` so a luminous K giant has a
  proportionally larger ray field than a faint K dwarf.
- **Flares amplitude**: pronounced for M dwarfs (Proxima-like
  activity); minimal for hot main-sequence; smoothly slow for
  supergiants. Same dual-driver as rays.

NO claim about "coronal temperature" or "X-ray emission color".
This is purely visual character tuning so the four named stars
read as distinct without overstating physics.

## M5 — Spect-missing fallback via absmag

**Effort**: ~2-3h (Path B + Path A combined).
**Scope tag**: atlas-native.
**Status**: pending.
**Depends on**: independent of M1-M4 (data fix), can run in
parallel; but easier to user-smoke after M4 so visual identity
is tied together.

### Premise correction (per Codex round-3 P2)

Original M5 plan claimed `radiusFromSpect(null, absmag)`
"already supports absmag fallback" — **false**.
`stellarPhysics.ts:369` does `if (!spect) return 1.0;` BEFORE
looking at absmag. The absmag parameter is consumed only by the
optional Stefan-Boltzmann refinement path (line ~402+) which
runs AFTER class-table lookup, i.e., only when spect IS present.
With spect="", absmag is never read.

M5 must do real work, not extend an existing path.

### Path A — runtime absmag fallback (~1-2h)

Extend `radiusFromSpect(spect, absmag)` to accept the
missing-spect case. When `spect` is null/empty AND `absmag` is
finite, derive an estimated radius from absmag alone using a
B-V-augmented Stefan-Boltzmann path (atlas already has B-V at
HygStellarMesh call site, can pass it through; or compute T_eff
from B-V via `temperatureFromBV` and combine with absmag for
L/L_sun then `R/R_sun = sqrt(L) × (T_sun/T_eff)²`). This handles
ANY star with missing spect, not just named ones. Pin per-named-
star radius assertions: Betelgeuse, Antares, Rigel, Proxima from
absmag+B-V should produce supergiant-class radii within ~30% of
catalog literature values.

### Path B — preserve named stars at canonicalization (~1h)

Fix `scripts/build-hyg-binary.js` `capSpectByFrequency` so it
always keeps the canonical class of any star in
`hyg-v1.names.json` (allowlist by HIP/proper-name/index — note:
the names sidecar today carries `hip` + `proper` + `bayer` +
`flam` + `con` + `index`; HD field is NOT exposed there, so
allowlist must use the available keys). Re-bake the 4 tier
`.bin` files. T6.2-β-β already showed how to re-bake; M5-B is a
delta. Net effect: Betelgeuse/Antares/Rigel get their real spect
strings restored in the binary; existing `radiusFromSpect(spect)`
does the right thing without runtime fallback work. Costs an L32
PNG re-bake flag (binary file change → screenshots if any depend
on starfield rendering — but they don't).

### Recommended: Path B + Path A combined

Path B fixes the specific-named-star regression that drove M5;
Path A is a defensive runtime fallback for any unnamed star
whose canonical class still ends up empty.

**Acceptance**: Betelgeuse renders supergiant-sized (~887 R_sol)
not Sun-sized. Same for Antares (~680 R_sol), Rigel (~78 R_sol),
Proxima (~0.15 R_sol). Pin per-star radius assertions in
`stellarPhysics.test.ts`.

`hyg:K` focus IDs instead of `BODIES_BY_ID`. Reads catalog +

stellarPhysics helpers (or new aggregator). Displays:

- Common name (sidecar `proper`/`bayer`/`flam`/`con`)
- Spectral class (parsed) + raw spect string
- Effective temperature (Ballesteros + MK refinement)
- Radius in R_sol
- Mass estimate from class + absmag
- Distance in parsec
- Apparent + absolute magnitude
- Sun comparison row ("Betelgeuse is 887× Sun radius")

Sidebar is HYG-blind today (resolves via BODIES_BY_ID); render
HygStarPanel as a parallel slot, gated on
`parseHygFocusId(focusId) !== null`.

fields; panel hides on focus to curated body (existing Sidebar
