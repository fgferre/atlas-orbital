## Independent investigation: lens-flare visual defect in atlas-orbital

You have read-only access to two repositories:

- atlas-orbital (port, current working dir): the project under review
- Gaia Sky (reference): cloned at `/tmp/gaiasky/`

### User-reported symptom

A user on Windows 11 / Chrome / NVIDIA running atlas-orbital in dev
mode reports a visual defect in the lens-flare post-process at certain
camera angles when the Sun is on-screen at solar-system distances
(roughly 5–30 AU from camera):

- A massive white halo dominating ~60% of the viewport, with sharp
  edges and visible chromatic-aberration banding (red / cyan fringes).
- A hexagonal sprite at ~lower-left, separate from the main halo.
- Frame-to-frame "flickering / bursting" — the artifact intensity
  varies noticeably as the camera rotates slowly.

The user says, verbatim: **"eu nunca vi esse defeito no Gaia"**
(I have never seen this defect in Gaia Sky). They run Gaia Sky
themselves and assert that Gaia's lens-flare at equivalent
conditions does NOT produce this artifact.

### Your task

Investigate independently. Determine — with file:line citations from
BOTH repos — whether atlas's runtime lens-flare output actually matches
Gaia's runtime lens-flare output at equivalent camera / Sun-on-screen
conditions. If it does not match, identify the divergence(s).

Do not assume the atlas team's parity claims are correct. Verify them.
Do not assume the user's observation is correct. Verify it. Where the

### Atlas team's analysis (presented as hypotheses to verify, NOT as fact)

The atlas team analysed the symptom and concluded the port is 1:1 with
Gaia. Their angle, summarised:

1. The COMPLEX `lens_flare()` shader is byte-for-byte ported. The
   10-iteration `lensFlareCircle` accumulator with the
   `cos(vec3(0.44, 0.24, 0.2)*8 + dist*4)*0.5+0.5` coloring naturally
   sums to white in the central region; `clamp(flareColor, 0, 1)`
   prevents HDR leakage. The hex blob is `regShape(N=6)`. So the
   visible defect is "by design".

2. LightGlow's `min(0.0001, viewAngle)` clamps halo size to a max
   `1.6 × textureScale = 0.65 × viewport` for any Sun closer than
   ~46 AU. So the giant halo is "expected at solar-system distance".

3. Frame-to-frame variation comes from `sin(l*30)` in
   `lensflare.frag.glsl:142` modulating as `light_pos` shifts.

4. atlas uses pmndrs `Effect` with `BlendFunction.ADD` and inlines the
   dirt + starburst modulation in the same fragment-shader pass; Gaia
   uses a separate `LensDirtFilter` two-pass via `PingPongBuffer` +
   `CombineFilter`. The team treats these as architecturally equivalent.

5. atlas's LightGlow vertex shader was moved back from fragment to
   vertex stage (T5.3b) per `lightglow.vert.glsl`. The team treats
   this as 1:1 with Gaia.

### Possible blindsides the atlas team may have missed

The team did NOT investigate these — please check each:

1. **Why doesn't Gaia show this defect?** If atlas's port is truly 1:1
   and the user genuinely runs both products, what filters or gates
   does Gaia's runtime apply that atlas's runtime does not? Trace the
   COMPLEX lens-flare path in `MainPostProcessor.java` end-to-end and
   compare with atlas's `PostProcessingPipeline.tsx` Effect order +
   `Scene.tsx` renderer config.

2. **First-frame init / uniform defaults.** Does atlas start with
   `u_lightPositions = (0, 0)` (= bottom-left UV corner) and
   `u_intensity = 1` for one frame before the per-frame driver
   overrides? Gaia's `LensFlareFilter` constructor defaults?

3. **Framebuffer format.** Gaia at `LensFlare.java:43-50` forces
   `Pixmap.Format.RGB888` (internal `GL_RGB16F`) for the lens-flare
   PingPong, citing AMD APU artifact concerns. atlas's pmndrs Effect
   sees whatever the EffectComposer chain provides — possibly RGBA8
   or float16 depending on prior Effect attributes. Investigate
   whether atlas's input buffer format causes the chromatic banding /
   white saturation.

4. **HDR vs LDR ordering of dirt modulation.** atlas inlines
   `flareColor.rgb * (dirt * 3 + starburst)` AFTER `clamp(flareColor,
   0, 1)` AND BEFORE the final ADD blend, all in HDR working space.
   Gaia's two-pass: `LensFlareFilter` writes flare to PingPong (HDR
   16F), `LensDirtFilter` reads PingPong + multiplies by dirt to
   PingPong-result, `CombineFilter` then ADDs the post-dirt result to
   the scene. Are these algebraically identical, or does the LDR/HDR
   boundary differ?

5. **Starburst offset semantics.** atlas's inline shader applies
   `mod(abs(radial - u_starburstOffset), 1.0)` with offset 0
   (constant for COMPLEX). Gaia's `LensDirtFilter` runs separately;
   COMPLEX never animates the offset. Are the sampling coordinates
   identical, or does atlas double-apply something?

6. **inputBuffer source.** atlas's `LensFlareEffect` reads the spiral
   occlusion samples from `inputBuffer` — what is that buffer at
   atlas's Effect-chain position? Pre-bloom? Post-bloom? Post-tonemap?
   Gaia's `lensflare.frag.glsl:181-202` reads `u_texture0` which is
   the `setInput(sourceTexture)` — what is `sourceTexture` in Gaia's
   pipeline? Could the buffer brightness differ at the moment the
   spiral samples?

7. **EffectAttribute.CONVOLUTION.** atlas's LensFlareEffect declares
   `attributes: EffectAttribute.CONVOLUTION`. What does this do in
   pmndrs? Does it force a depth/normal buffer dependency, prevent
   merging with adjacent Effects, change render-target allocation?

8. **light intensity scaling chain.** Gaia's `LensFlare.java:65-67` →
   `LensFlareFilter.setLightPositions(nLights, positions, intensities)`.
   atlas's `LensFlareEffect.setLight(uv, 1.0)`. Is the per-light
   intensity calibration identical?

9. **u_color.** Gaia at `LensFlareFilter.java:32` defaults `u_color
   = (1, 1, 1)`. atlas same. But verify `u_color` is actually read in
   the COMPLEX branch — `lensflare.frag.glsl:140` uses `u_color`
   only for the `circColor` argument to `lensFlareCircle`, where the
   loop body OVERWRITES `color` via the cos() expression at line 131.
   So `u_color` may be DEAD in COMPLEX. If so, irrelevant — but
   verify.

10. **Bloom interaction.** atlas defaults `bloomIntensity = 0` per
    T5.3a (matches Gaia). But the PRESET_DEFAULTS for the user's
    setup may have `bloomEnabled = true`. If bloom is on AND bloom
    samples HDR pixels brighter than threshold, the saturated lens-
    flare output (additively blended on the scene) could feed back
    into bloom on the next frame.
